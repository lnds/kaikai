# RB-tree vs C/C++ — 2026-09-11 (retires the 2026-06-02 boxing diagnosis)

Re-measurement of the canonical Perceus red-black tree workload
(`examples/perceus/rb_tree_bench.kai`, 1 M random inserts) on kaikai
v0.117.0 (HEAD `e461d621`). This supersedes
`docs/benchmarks/rb_tree_2026-06-02.md`, whose headline **and root-cause
attribution** are both dead.

This is a **measurement doc**: no compiler, runtime or stdlib code was
changed. One experimental patch was applied to `stage2/runtime.h` to run
an A/B ablation and then reverted; the tree is clean.

## Hardware / configuration

| Variable | Value |
| --- | --- |
| Host | Apple M4 Pro, macOS (Darwin 25.6.0 arm64) |
| kaikai | v0.117.0 (HEAD `e461d621`), edition hanga-roa |
| kaikai build | `bin/kai build` → C backend, `cc -O2 -std=c99` |
| C reference | `clang -std=c11 -O2` (intrusive RB, parent pointers) |
| C++ reference | `clang++ -std=c++17 -O2` (`std::set<int64_t>`) |
| Workload | 1,000,000 LCG-seeded inserts (Numerical Recipes ranqd1, mod 2^31-1) |
| Metric | `/usr/bin/time -l`, 5 interleaved runs per column, spread < 1% |

Koka was **not** re-measured (not installed on this host). Every Koka
figure below is quoted from the 2026-07-06 `docs/koka-parity-plan.md`
run and labelled as such — do not read it as a same-session column.

## Headline numbers

| Implementation | Wall | Instructions | Peak RSS | vs C wall | vs C instr |
| --- | ---: | ---: | ---: | ---: | ---: |
| C (hand-written intrusive RB) | **462 ms** | **0.453 G** | **47 MB** | 1.00× | 1.00× |
| C++ `std::set<int64_t>` | 475 ms | 0.625 G | 47 MB | 1.03× | 1.38× |
| **kaikai** (v0.117.0) | **651 ms** | **2.577 G** | **65 MB** | **1.41×** | **5.69×** |

Per insert: kaikai 2577 instructions, C 453, C++ 625. At tree height 29
(~20 levels of descent) that is ~129 instructions per level for kaikai
against ~23 for C.

### Wall and instructions disagree, and the disagreement is the finding

kaikai retires **5.69× C's instructions** but takes only **1.41× C's
wall**. The workload is a random descent over a 65 MB tree: it is
memory-latency-bound, and kaikai's surplus instructions largely hide in
cache-miss shadow. Two consequences:

- **Wall ratios understate the real compute gap on this bench.** The
  1.41× is a property of the memory system as much as of the compiler.
- **Instruction count is the hardware-independent number.** Use it when
  comparing across machines or across months; use wall only within one
  session against a same-session baseline.

This is why the 2026-06-02 headline (2.64× C wall) and this one (1.41× C
wall) cannot be compared as progress: in June C ran this workload in
250 ms, here it takes 462 ms. **kaikai's own wall barely moved (660 →
651 ms) while its instruction count fell 8.37 G → 2.58 G (3.2×).** The
instruction column is where the last three months actually show up.

## What the 2026-06-02 doc got wrong

That doc closed by naming the cause of its 7.7× instruction gap to Koka:

> It is the boxed↔unboxed `Int` frontier. Every key comparison and every
> argument pass still routes a small `Int` through a `kai_int` box.

**That diagnosis was incorrect when it was written**, not merely stale.
Tagged-Int landed in `06289fbc` ("Koka tagged-Int value representation
in stage2 runtime") on **2026-06-01** — one day *before* the benchmark,
and `git merge-base --is-ancestor 06289fbc fcffd3c` confirms it was in
the measured binary. The gap was attributed to a box that the measured
build no longer allocated.

Verified on today's build, at the level the claim was made:

- `kai_tagged_int` / `kai_is_value` (`stage2/runtime.h:791-810`) encode a
  63-bit immediate `Int`, an explicit port of Koka's
  `kk_integer_from_small`.
- Disassembly of `kaiu_rb_tree__insert_loop` reads the key as an inline
  slot (`ldr x8, [x23, #0x8]` — slots begin at the union offset, 8), with
  no load through a `kai_int` cell.
- Node size is 48 B (8 B packed header + 5×8 slots), identical to the C
  reference's `rb_node` and to Koka's cell.

`docs/koka-parity-plan.md` (2026-07-06) already recorded this under
*"What we already match (verified, not assumed) → Raw Int slots …
Parity."* The June conclusion had been superseded in July; the honesty
targets and roadmap were never updated to match.

## The July allocation gap is also closed

`docs/koka-parity-plan.md` called allocation traffic "the smoking gun":
5.24 allocated cells per insert against Koka's ~1, with 4.24 captured
reuse tokens thrown away. Re-run today at the same N=100,000 and with the
same counter:

| counter (N=100K) | 2026-07-06 | 2026-09-11 | |
| --- | ---: | ---: | --- |
| `alloc_total` (variant) | 523,643 (5.24/insert) | **100,027 (1.00/insert)** | −80% |
| `incref_total` | 1,118,570 (11.2/insert) | **200,006 (2.00/insert)** | −82% |
| `decref_total` | 1,118,582 (11.2/insert) | **200,031 (2.00/insert)** | −82% |

At N=1 M: `alloc_total=1000025`, `free_total=1000022`, `leaked=3`,
`reuse_in_place=6301528`. One fresh cell per insert is Koka's
by-construction figure — **allocation traffic is at parity, and the
allocator lever named in July is spent.**

## Where the remaining 5.69× actually lives

Static analysis of `kaiu_rb_tree__insert_loop` (801 machine instructions
for a loop C expresses in ~20). Guards, counted by pattern:

| repeated guard | occurrences |
| --- | ---: |
| `ldadd` — **atomic** refcount update | 26 |
| tag byte load (`ldrb [x, #0x4]`) | 19 |
| null check (`cbz`) | 19 |
| tagged-pointer value test (`tbnz w, #0`) | 17 |
| immortal check (`rc == INT32_MAX`) | 14 |
| `kai_nthreads > 1` load + compare | 13 |

Every `dup`/`drop` walks a four-test chain — *is it an immediate value? →
is it null? → is it immortal? → are we multi-threaded and is this a
Fiber?* — before touching the count. The cost is no longer allocation,
no longer boxing, and no longer RC *volume* (2 increfs per insert is
already minimal); it is the **per-operation guard chain and its
atomics**.

Two observations for whoever takes this next:

- `kai_nthreads` is fixed after startup but is re-loaded from memory on
  every dup on the hot path.
- 26 atomic RMWs sit in the hottest loop of the program. On ARM an
  `ldadd` costs more than its instruction count suggests: it constrains
  reordering around it.

Neither is a proposed fix; both are measured facts. Any change here is a
runtime/codegen lane with its own before/after instruction counts.

## One hypothesis that measurement refuted

`KAI_CTR_INC` (`stage2/runtime.h:901`) is `atomic_fetch_add_explicit` on
*shared globals* (`kai_rc_incref_total` / `kai_rc_decref_total` are
`KAI_RT_ATOMIC_COUNTER`, not the thread-local `KAI_RT_COUNTER` used by
the rest), and it is compiled into every build — only the exit report is
env-gated. That looked like an obvious tax on the hot path.

A/B, same source, same flags but `-DKAI_NO_RC_CTR` neutralising the
macro, 5 interleaved serial runs:

| | instructions | wall |
| --- | ---: | ---: |
| counters ON (shipping default) | 2.578 G | 0.599–0.682 s |
| counters OFF | 2.549 G | 0.629–0.661 s |

**1.2% of instructions; wall difference inside run-to-run noise.**
Refuted — the always-on counters are not a meaningful cost, and the
runtime comment claiming "~ns per allocation" is accurate. The 26 hot
`ldadd`s come from the refcount itself, not from telemetry. The patch
was reverted.

## Reproduction

```sh
bash examples/perceus/rb_tree_bench.sh 5        # wall + RSS table

# instruction counts (macOS; Linux: perf stat -e instructions)
bin/kai build examples/perceus/rb_tree_bench.kai -o /tmp/rb_kai
clang   -std=c11   -O2 examples/perceus/rb_tree_bench_c.c -o /tmp/rb_c
clang++ -std=c++17 -O2 -DBENCH_STDSET examples/perceus/rb_tree_bench_c.c -o /tmp/rb_cxx
for b in /tmp/rb_kai /tmp/rb_c /tmp/rb_cxx; do /usr/bin/time -l $b; done

# RC ledger
KAI_TRACE_RC=1 /tmp/rb_kai
```

## What is settled vs open

- **Settled:** allocation traffic at parity (1.00 cell/insert), RC volume
  minimal (2 incref/insert), garbage-free (`free_total == alloc_total`),
  48 B cells, raw `Int` slots with no `kai_int` box in the descent.
  Boxing and allocation are both spent levers.
- **Settled (negative):** always-on RC telemetry counters are not a
  measurable cost.
- **Open:** the per-RC-operation guard chain and its atomics — the
  residue of the 5.69× instruction ratio. Unquantified per-guard; no lane
  assigned.
- **Not measured here:** Koka on this host, and the native (LLVM) backend
  — this kaic2 was built without libLLVM, so every figure is the C
  backend.
