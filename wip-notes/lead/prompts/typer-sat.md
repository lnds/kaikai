NOTES FOR YOUR AREA
- These are the typer's helper modules. `TyCon(SymId, [Ty])`: a type's identity is its id; its name (printing in `type_text.kai`, mangling keys, diagnostics, dumps) comes from the table: `decl_name(tab, s)` → the printers / key builders take `tab: SymTab` (record their new signatures in API.md; many files call `type_text`). `Label { sym, ty_args }`, `RL(DeclRef, targs)`.
- `tycon_scheme_home.kai` (`tsh_*`: where a WRITTEN type name becomes an id; `THE`, `TyRes` hold strings beside ids), `tycon_ref.kai`, `component_ids.kai`, `type_stamp.kai`: this is the resolver side for type names inside the typer: text in (`DrWritten(q, name)`), id out (`TyCon(sym, args)`, `DrSym(sym)`). With `TyCon` holding no name, `tsh_tycon(v, name, args)` must produce an id or the error placeholder (`sym_none()`); a scalar or a type parameter is not a `TyCon`. `type_stamp.kai` leaves every `TyName` it can settle as `TyName(DrSym(sym), args)`; `type_ids_check.kai` (`--check-type-ids`) reports the ones still written that should not be.
- `tycon_home.kai`, `tycon_pat.kai` run AFTER the typer and existed to stamp a home STRING on types and patterns: with ids in the nodes most of what they do is done; make them compile preserving what still has meaning (a pattern must end up `PVariant(DrSym(constructor id), …)`), and report what has become dead.
- `effect_instance*.kai` build the instance keys of parametric effects from types: key text is built from ids (and scalar spellings via `scalar_ty.kai`), never from a `TyCon` name.
